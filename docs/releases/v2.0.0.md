## 2. 亮点（按主题）

### 2.1 远程记忆架构

- 插件从「本地 Markdown 文件」重构为 **纯远程薄客户端**：本地不再读写 `~/.config/opencode/memory/`，所有读写走 Worker REST API。
- 领域模型与 `MemoryClient` 下沉到 `packages/shared`，OpenCode 插件、pi 扩展、Web 与 Worker 共用同一套类型和客户端。
- `memory` 工具语义从文件操作改为记录操作：`add` / `search` / `get` / `update` / `delete` / `list`；记录按 `id` 操作。
- 会话启动时由服务端 `/api/context` 组装注入内容（身份 + 偏好 + 规则 + 项目知识 + 最近 digest），调整注入策略无需重新发布插件。

### 2.2 D1 / Vectorize / 检索

- D1 统一单表 `memories`（`daily` / `fact` / `instruction` / `digest`）+ `memory_entities`（分面实体）+ `memory_links`（supersedes / contradicts 演化链）。
- 混合检索：FTS 全命中为桶 A、部分命中/向量召回为桶 B，桶内 RRF 融合；分面硬过滤在 topK 截断前执行，避免漏召。
- 写入同步路径只做 D1 插入；embedding、Vectorize upsert、fact 实体抽取/查重/新陈代谢通过 `waitUntil` 异步执行。
- 每日 digest cron（UTC `0 20 * * *`，默认东八区 04:00）：昨天的 daily 汇总为一条 digest，占位行 + 部分唯一索引保证幂等与可重跑。
- 向量 metadata 记录 embedding 模型版本（`@cf/qwen/qwen3-embedding-0.6b`，1024 维），支持换模型后按批 reindex。

### 2.3 MCP

- 新增 `/mcp` Streamable HTTP 无状态 JSON-RPC 端点（`initialize` / `tools/list` / `tools/call`），与 REST 共享 service 层。
- 提供 7 个工具：`memory_add` / `memory_search` / `memory_get` / `memory_update` / `memory_delete` / `memory_context` / `memory_digest_status`。
- 不引入 MCP SDK / Durable Object，保持 Worker 轻量。

### 2.4 OAuth 与认证

- Web 控制台使用 GitHub OAuth2 登录；`OAUTH_ALLOWLIST` 为空时首个登录者认领实例，之后仅允许已有用户登录。
- 插件、MCP、迁移脚本统一使用可撤销的 API Token（`opm_` 前缀，SHA-256 哈希存储）。
- 新增 `users` / `api_tokens` 表；废弃离线 JWT 生成脚本。
- `/api/admin/remap-user` 增加 `X-Admin-Secret` 鉴权；CORS 收紧为显式来源；reindex 支持分批推进，避免 Worker 超时。

### 2.5 Web 控制台

- 适配 v2：GitHub OAuth 登录、Token 管理页（创建/查看/撤销）、统一记忆列表与详情。
- 顶部导航 + 独立记忆页 + 总览 + AI 问答；支持结构化记忆与来源引用展示。
- Web 静态产物随 Worker assets 部署（`apps/web/dist`）。

### 2.6 pi 扩展

- 新增 `apps/pi-extension`：pi coding agent 原生 TypeScript 扩展（pi 不支持 MCP）。
- 提供 `memory_add/search/get/update/delete/list` 六个工具，并在会话开始注入服务端组装的上下文。
- 支持 `OPM_API_URL` / `OPM_API_KEY`，也可回退读取 `opencode.json` 的 `remote` 配置。

### 2.7 迁移与运维

- 新增迁移 `0010_unified_schema.sql` / `0011_migrate_data.sql` / `0012_drop_legacy.sql`：建统一表 → 搬迁 instructions/learnings/dailies → 删除旧表与三套 FTS → 重建单套 FTS。
- 新增 `scripts/migrate-v2.ts`：旧 `user_id` 归属映射 + 全量/增量 reindex（按批推进）。
- 清理 `generate-jwt` / `jwt-gen` / `backfill-text-fts` / `reindex-memories` / `smoke-test` 等废弃脚本。
- ADR-007 记录统一 schema、两桶分层搜索、远程-only 的决策。

### 2.8 工程与 CI

- 重组为标准 pnpm monorepo（`apps/*` + `packages/*`），CI/CD 与发布链路改为 pnpm + Bun。
- 新增 PR 自动审查（Pi Agent）与 Issue 智能分类工作流；PR 审查输出 `review-report.md` 交付物。
- 发布链路保持三段式：`release.yml` 校验并创建 tag → `release-draft.yml` 生成 draft release → `publish-npm.yml` 在 release published 后发布 npm。

## 3. 破坏性变更

1. **npm 包改名**：`@devcxl/opencode-memory` → `@devcxl/cabbage-memory`。
   - 旧包停留在 `1.2.0`，不会收到 `2.0.0` 更新；必须修改 `opencode.json` 的插件名。
   - 插件内部配置匹配器兼容旧包名，但 OpenCode 仍按配置里的包名加载，改名不可省略。
2. **移除本地模式**：v2 仅支持远程模式。`MEMORY.md` / `USER.md` / `IDENTITY.md` / `daily/*.md` 等本地文件不再读取或写入。
3. **工具语义变化**：`read` / `write` / `edit` / `delete by timestamp` 等文件动作被 `add` / `search` / `get` / `update` / `delete by id` / `list` 取代；依赖旧工具参数的提示词与自动化需要改写。
4. **必须部署后端并配置 Token**：没有 `OPM_API_KEY` 时插件直接报错；不再有「无配置即可本地使用」的路径。
5. **配置结构变化**：从 `"plugin": ["@devcxl/opencode-memory"]` 变为带 `remote.apiUrl` / `remote.apiKey` 的二元组；环境变量仍为 `OPM_API_URL` / `OPM_API_KEY`，但旧远程预览版的 `mode` 字段与 `OPM_MODE` 开关不再使用。
6. **v1.2.0 本地数据不会自动迁移**：v1.2.0 是本地 Markdown 插件，仓库内没有「本地 Markdown → 远程记录」的导入脚本；需要手工重新 `add`，或自行调用 REST API 导入。
7. **旧的远程预览数据需要显式 remap**：`scripts/migrate-v2.ts --old-user-id` 只适用于曾部署过 `cloudflare-memory` / 远程预览版的用户；v1.2.0 本地用户没有服务端 `user_id`，跳过该步骤。
8. **Node 版本**：CI/发布使用 Node 24；插件产物为 Node ESM bundle（`dist/index.js`）。

## 4. 迁移步骤

### 4.1 从 v1.2.0（本地 Markdown）升级

1. 按 4.3 完成 Worker、D1、Vectorize 与 secrets 部署（本仓库 v1.2.0 不含 Worker 后端，必须全新部署；若你同时使用过独立的 `cloudflare-memory` 项目，见 4.2）。
2. 首次 GitHub 登录 Web 控制台，在个人中心生成 API Token（`opm_...`）。
3. 修改 `~/.config/opencode/opencode.json`：

   ```json
   {
     "plugin": [
       [
         "@devcxl/cabbage-memory",
         {
           "remote": {
             "apiUrl": "https://<worker-url>",
             "apiKey": "env://OPM_API_KEY"
           }
         }
       ]
     ]
   }
   ```

4. 设置环境变量（优先级高于配置文件）：

   ```bash
   export OPM_API_URL="https://<worker-url>"
   export OPM_API_KEY="opm_xxx"
   ```

5. 本地 Markdown 记忆需手工导入：逐条调用 `memory add`，或用 `POST /api/memories` 批量导入。仓库当前**没有**自动导入脚本。

### 4.2 从 cloudflare-memory / 远程预览版升级

README 的三步迁移命令如下（**注意工作目录**：仓库根目录没有 `wrangler.toml`，wrangler 命令必须在 `apps/api` 下执行）：

```bash
cd apps/api
wrangler d1 migrations apply memory-db --remote
cd ../..
pnpm --filter @devcxl/cabbage-memory-web build
pnpm deploy:api
```

```bash
cd apps/api
wrangler secret put JWT_SECRET
wrangler secret put GITHUB_CLIENT_ID
wrangler secret put GITHUB_CLIENT_SECRET
# 迁移旧 user_id 时必需；未设置时 /api/admin/remap-user 返回 403
wrangler secret put ADMIN_SECRET
```

首次 GitHub 登录并生成 API Token 后执行 remap + reindex（README 原命令缺少 `--admin-secret`，会导致 403）：

```bash
npx tsx scripts/migrate-v2.ts \
  --url https://<worker-url> \
  --token opm_xxx \
  --old-user-id <legacy JWT sub> \
  --admin-secret <ADMIN_SECRET> \
  --force-reindex
```

### 4.3 全新部署（v1.2.0 用户与首次部署）

```bash
cd apps/api
wrangler d1 create memory-db          # 将返回的 database_id 写入 wrangler.toml
wrangler vectorize create memory-index --dimensions=1024 --metric=cosine
wrangler secret put JWT_SECRET
wrangler secret put GITHUB_CLIENT_ID
wrangler secret put GITHUB_CLIENT_SECRET
# 可选：wrangler secret put ADMIN_SECRET（仅迁移旧数据时需要）
cd ../..
pnpm --filter @devcxl/cabbage-memory-api db:migrate
pnpm --filter @devcxl/cabbage-memory-web build
pnpm deploy:api
```

GitHub OAuth App 回调地址：`https://<worker-url>/auth/github/callback`。
`OAUTH_ALLOWLIST` 可选（逗号分隔 GitHub id/login）；留空时首个登录者认领实例。

## 7. 发版步骤

> 前置：v2 的 Worker 必须先部署并验证（`/health` 返回 OK），再发布 npm 包，避免用户升级插件后无后端可用。

### Step 0 — 预检（只读）

```bash
git status --short                     # 应为空
git log --oneline -1                   # 发布分支最新提交
git tag -l 'v2.0.0'                    # 应为空
node -p "require('./apps/plugin/package.json').version"   # 2.0.0
gh release list --limit 5               # 最新应为 v1.2.0
```

### Step 1 — 合并默认分支

`release.yml` 要求目标 ref 必须在 `origin/main` 提交链上，所以必须先合并：

```bash
gh pr view 5 --json mergeable,mergeStateStatus   # MERGEABLE / CLEAN
gh pr merge 5 --merge                            # 保留提交历史；squash 也可行
git checkout main
git pull --ff-only origin main
```

等待 main 上的 CI 通过：

```bash
gh run list --branch main --limit 3
gh run watch <run-id>
```

### Step 2 — 运行 Release workflow

```bash
gh workflow run release.yml -f ref=main
gh run list --workflow release.yml --limit 1
gh run watch <run-id>
```

该工作流会：安装依赖 → typecheck → format check → build plugin → `npm pack --dry-run` → 读取 `apps/plugin/package.json` 版本 → 校验 tag 不存在 → 校验 `HEAD` 是 `origin/main` 祖先 → 创建并推送 `v2.0.0`。

### Step 3 — 等待 draft release

tag 推送后 `release-draft.yml` 自动触发：

```bash
gh run list --workflow release-draft.yml --limit 1
gh release list --limit 5
```

确认出现 `Release v2.0.0`，状态为 Draft；核对 tag 指向 main 上的提交。

### Step 4 — 填写发布说明并发布

将本文第 2–6 节内容整理进 GitHub Release 描述（draft 默认由 `generate_release_notes` 生成，需要人工覆盖/补充），然后：

```bash
gh release edit v2.0.0 --draft=false
```

`release: published` 事件触发 `publish-npm.yml`：校验 tag 与包版本一致 → 校验 release 提交在 `origin/main` 链上 → typecheck / format / build / pack → `npm publish --tag latest`。

### Step 5 — 发布后验证

```bash
npm view @devcxl/cabbage-memory version dist-tags.latest
npm view @devcxl/cabbage-memory@2.0.0 dist.tarball
gh run list --workflow publish-npm.yml --limit 1
```

同时验证：

- `https://<worker-url>/health` 返回 `OK`；
- Web 控制台可 GitHub 登录并生成 Token；
- 用新 Token 调用 `POST /api/memories` 与 `POST /api/memories/search`；
- MCP `initialize` / `tools/list` 返回 7 个工具；
- OpenCode 配置新包名后，`memory add/search` 可用。

### 回滚

- npm 包：发布 72 小时内可 `npm unpublish @devcxl/cabbage-memory@2.0.0`；超过 72 小时用 `npm deprecate` 并发布修复版。
- GitHub Release / tag：将 release 改回 draft 或删除 tag（`git push origin :refs/tags/v2.0.0`），但已 publish 的 npm 包不会自动回滚。
- Worker：`wrangler rollback` 回退上一个 deployment；D1 迁移 0012 会删除旧表，无法靠回滚 Worker 恢复，生产迁移前必须先备份 D1（D1 Time Travel 可短期回退）。
